01 · Le basi

Processi, multiprogrammazione e thread

Un programma è un file sul disco; diventa processo quando la CPU lo esegue. Il sistema operativo tiene in esecuzione tanti processi insieme alternandoli sulla CPU: è la multiprogrammazione. Il trucco sta nei tempi morti.

Perché alternare conviene

Un processo non calcola e basta: ogni tanto aspetta (un file dal disco, un tasto, la rete). Durante l'attesa la CPU, da sola, resterebbe ferma. Premi play e confronta.

usa la CPU aspetta (I/O) CPU ferma

🧱 Processo

Un programma in esecuzione con la sua memoria privata (codice, dati, stack, heap). Due processi sono isolati: non vedono le variabili l'uno dell'altro. Creare e far comunicare processi costa.

🧵 Thread

Un flusso di esecuzione dentro un processo. Più thread dello stesso processo condividono la memoria (le stesse variabili): comunicano facilmente, ma proprio per questo possono interferire. Sono «leggeri».

La memoria condivisa dei thread è comoda e pericolosa: è la radice di tutti i problemi di questo corso. In Java un thread si crea estendendo Thread o implementando Runnable, e si avvia con start().

03 · Tre modi di stare insieme

Indipendenti, cooperanti, in competizione

I processi su un sistema hanno rapporti diversi. Capirli serve per sapere cosa dobbiamo gestire nel resto del corso.

Indipendenti

Evolvono ognuno per conto suo, senza scambiarsi nulla. Nessun problema da risolvere.

Cooperanti

Collaborano a un obiettivo comune producendo e usando dati condivisi. Hanno bisogno di comunicare e sincronizzarsi. Es.: il correttore di Word mentre scrivi, un gioco online.

In competizione

Potrebbero essere indipendenti, ma litigano per una risorsa limitata (CPU, stampante, un file). Vanno coordinati, altrimenti si bloccano a vicenda.

Grafi di precedenza: chi prima, chi dopo, chi insieme

Un grafo di precedenza dice in che ordine devono avvenire le operazioni. Alcune sono in sequenza, altre si possono fare in parallelo. Due notazioni per descriverlo nel codice:

fork / join

fork lancia un'attività in parallelo; join aspetta che finisca. Flessibile: puoi biforcare e ricongiungere dove vuoi.

S1;
fork S3;   // S2 e S3 in parallelo
S2;
join;      // aspetta S3
S4;

cobegin / coend

Tutto ciò che sta tra cobegin e coend parte insieme; si prosegue solo quando tutte le attività sono finite. Più leggibile, ma meno libero.

S1;
cobegin
  A; B; C;   // tutti e tre insieme
coend
S2;          // dopo che A, B, C finiscono
04 · Il problema, dal vivo

La race condition

Due thread aumentano di 1 lo stesso contatore. Sembra banale, ma x = x + 1 non è un'operazione sola: la CPU la spezza in tre passi — leggi x in un registro, incrementa il registro, riscrivi x. Se il sistema operativo cambia thread nel mezzo, un aggiornamento va perso. Decidi tu l'ordine dei passi e guarda.

variabile condivisa x = 0
Thread 1
  1. reg₁ ← x –
  2. reg₁ ← reg₁ + 1
  3. x ← reg₁
Thread 2
  1. reg₂ ← x –
  2. reg₂ ← reg₂ + 1
  3. x ← reg₂

Ogni thread fa +1: alla fine x dovrebbe valere 2. Avanza i due thread a turno — o tutto uno e poi l'altro — e vedi se ci riesci… o se perdi un aggiornamento.

Il risultato dipende dall'ordine con cui i thread vengono eseguiti — un ordine che tu non controlli. Un bug che a volte c'è e a volte no: il più infido che esista. La porzione di codice che tocca la variabile condivisa si chiama sezione critica.

05 · La regola

Sezione critica e mutua esclusione

La cura alla race condition è garantire la mutua esclusione: nella sezione critica può starci un thread per volta. Gli altri aspettano il loro turno. Una buona soluzione deve rispettare tre requisiti.

① Mutua esclusione

Se un processo è nella sezione critica, nessun altro può entrarci nello stesso momento.

② Progresso

Se la sezione è libera e qualcuno vuole entrare, la scelta di chi entra non può essere rimandata all'infinito.

③ Attesa limitata

Un processo che vuole entrare deve riuscirci entro un tempo finito: niente attese eterne (niente starvation).

Tre proprietà da ricordare

Safety — «non succede mai niente di male»: due thread non sono mai insieme nella sezione critica, i dati restano coerenti.
Liveness — «prima o poi qualcosa di buono succede»: i processi avanzano, nessuno resta bloccato per sempre.
Fairness — «a ciascuno il suo turno»: nessun processo viene sistematicamente scavalcato dagli altri.

Lo strumento storico per ottenere la mutua esclusione, inventato da Edsger Dijkstra nel 1965, è il semaforo. È la prossima sezione.

06 · Lo strumento

I semafori di Dijkstra

Un semaforo è un intero con una coda, su cui agiscono due sole operazioni atomiche. P() (o wait, dall'olandese proberen, «provare»): decrementa; se diventa negativo, il processo si blocca in coda. V() (o signal, verhogen, «incrementare»): incrementa; se c'era qualcuno in attesa, lo sveglia. Provalo.

Con S=1 solo un processo per volta entra: è un mutex. Premi P() con più processi e guarda chi entra e chi finisce in coda; poi libera con V().

Semaforo binario (mutex)

Vale 0 o 1. Fa mutua esclusione: protegge una sezione critica. Si usa a coppie P…sezione critica…V.

Semaforo mutex = 1;
P(mutex);   // entro
  x = x + 1;        // sezione critica
V(mutex);   // esco

Semaforo contatore & rendez-vous

Inizializzato a N, concede l'accesso a N processi insieme (es. N copie di una risorsa). Due semafori incrociati creano un rendez-vous: due processi si aspettano a un punto d'incontro.

// spin lock (attesa attiva): spreca CPU
while (occupato) ;   // gira a vuoto!
// il semaforo invece BLOCCA e libera la CPU
07 · Problema classico #1

Produttori e consumatori

Un produttore mette oggetti in un buffer di capacità limitata, un consumatore li toglie. Il produttore deve fermarsi se il buffer è pieno, il consumatore se è vuoto. Si risolve con tre semafori: vuoti, pieni e mutex.

    buffer.inserisci(dato);             dato = buffer.togli();
  V(mutex);                            V(mutex);
  V(pieni);   // +1 da consumare        V(vuoti);   // +1 posto libero
08 · Problema classico #2

Lettori e scrittori

Una risorsa condivisa (es. un archivio). Molti lettori insieme non danno problemi: leggono e basta. Ma uno scrittore deve avere accesso esclusivo: mentre modifica, nessun altro può leggere o scrivere. Aggiungi lettori e scrittori e guarda chi entra e chi aspetta.

09 · Problema classico #3

I cinque filosofi a cena

Cinque filosofi attorno a un tavolo, cinque forchette, una tra ogni coppia. Per mangiare servono entrambe le forchette vicine. Se tutti prendono insieme la forchetta sinistra e aspettano la destra… nessuno mangia più: deadlock. Guardalo succedere, poi applica la soluzione.

Premi «tutti sinistra» per innescare lo stallo: ognuno tiene una forchetta e aspetta per sempre quella del vicino. La soluzione asimmetrica: un filosofo prende prima la destra, e il cerchio dell'attesa si spezza.

10 · Lo stallo

Deadlock e grafo di Holt

Un deadlock (stallo) è un gruppo di processi ciascuno in attesa di una risorsa tenuta da un altro del gruppo: un'attesa circolare da cui non si esce. Serve e basta che valgano quattro condizioni insieme (Coffman).

Mutua esclusione

La risorsa è usabile da un processo per volta.

Hold & wait

Un processo tiene una risorsa e ne chiede altre.

No preemption

Una risorsa non può essere tolta a forza: la rilascia solo chi la tiene.

Attesa circolare

Esiste un ciclo P₁→P₂→…→P₁ di attese.

Il grafo di Holt, con la riduzione passo-passo

Il grafo di Holt disegna la situazione: i processi sono cerchi, le risorse rettangoli con un pallino per istanza. Un arco risorsa → processo è un'assegnazione; un arco processo → risorsa è una richiesta ancora da soddisfare. Il grafo è riducibile se si riesce a far terminare tutti: se ci si riesce del tutto, niente stallo. Carica uno scenario e riduci.

Scegli uno scenario qui sopra. Poi premi Riduci di un passo: a ogni passo cerchiamo un processo con sole richieste soddisfatte (solo archi entranti), lo facciamo terminare e liberiamo le sue risorse.

Evitare lo stallo: l'algoritmo del banchiere

Dijkstra di nuovo. Il sistema concede una risorsa solo se dopo resta in uno stato sicuro: esiste almeno un ordine in cui tutti i processi possono finire. Come un banchiere che presta solo se è certo di rientrare.

11 · Nel linguaggio

Monitor e concorrenza in Java

Usare i semafori a mano è facile da sbagliare: basta una P() senza la sua V() e il programma si blocca. Il monitor è un costrutto di più alto livello: un oggetto in cui i metodi sono già in mutua esclusione. In Java il monitor è integrato nel linguaggio con synchronized.

synchronized — mutua esclusione automatica

Un metodo synchronized acquisisce il lock dell'oggetto all'ingresso e lo rilascia all'uscita, anche in caso di errore. Un thread per volta, senza P/V manuali.

class Conto {
  private int saldo = 0;
  public synchronized void deposita(int n) {
    saldo = saldo + n;   // ora è sicuro
  }
}

wait() / notify() — sincronizzazione

Dentro un monitor, wait() sospende il thread e rilascia il lock; notify() risveglia chi aspetta. È così che si realizzano produttori-consumatori senza semafori espliciti.

synchronized void preleva() throws InterruptedException {
  while (vuoto)
    wait();        // aspetta un dato
  ...              // consuma
  notify();        // sveglia un produttore
}

Gli strumenti pronti: java.util.concurrent

Oggi raramente si scrivono i semafori a mano: la libreria standard offre mattoni già corretti e collaudati.

Semaphore

Il semaforo di Dijkstra, bello e pronto: acquire() è la P(), release() è la V().

ReentrantLock

Un lock esplicito più flessibile di synchronized: lock() / unlock(), con tentativi e timeout.

BlockingQueue

Una coda thread-safe che è già un produttori-consumatori: put() blocca se piena, take() se vuota.

import java.util.concurrent.Semaphore;

Semaphore mutex = new Semaphore(1);   // binario
mutex.acquire();          // P()
try {
  saldo = saldo + 1;      // sezione critica
} finally {
  mutex.release();        // V() — sempre, anche in caso di errore
}

In sintesi

  1. Più flussi che condividono memoria possono interferire: race condition.
  2. La cura è la mutua esclusione sulla sezione critica.
  3. Lo strumento base è il semaforo (P/V); i problemi classici si risolvono combinandone alcuni.
  4. Coordinare male porta al deadlock: lo si riconosce col grafo di Holt e lo si evita col banchiere.
  5. In pratica si usano i monitor (synchronized) e java.util.concurrent.
